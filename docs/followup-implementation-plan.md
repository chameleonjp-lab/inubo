# イヌボー 後続対応の実装計画書

> **実装担当へ:** `superpowers:executing-plans` または `superpowers:subagent-driven-development` を使い、各工程のチェック欄と合格条件に沿って進める。本書は計画であり、未実装・未検証の項目を完了扱いにしない。

**目的:** 自由操作を競技と練習の両方へ接続し、38技を任意の見本として使えるようにする。見た目と接触の一致、旧記録の保全、15言語対応、iPhoneでの確認を完了する。

**構成:** 既存の「技の練習」を拡張し、新ルールの競技とは姿勢・入力・接触の計算を共有する。姿勢・接触位置を計算側で一度決め、描画も同じ値を使う。全技の画面操作、旧記録の保全、実機での確認は別々に合否を残す。

**使用環境:** 現行のTypeScript、Three.js、Vite、Vitest、Playwright、GitHub Actions／Pagesを使う。依存ライブラリの更新、新しい有料サービスの導入は本計画に含めない。

**根拠:** [要件仕様書](game-requirements.md)、[既存実装計画](implementation-plan.md)、[38技の実装計画](trick-motion-implementation-plan.md)、2026年11月14日の後続対応一覧と計画書作成依頼。

## 4. F01 — 判定と表示が共有する姿勢を作る

**作成:** `src/game/lab-geometry.ts`、`src/game/lab-pose.ts`、`src/view/lab-rig.ts`、`tests/lab-pose.test.ts`、`tests/lab-rig.test.ts`。**変更:** `src/game/trick-lab.ts`、`src/view/trick-lab.ts`、`src/view/scene.ts`。新ルールの競技と練習はG02で同じ共通モデルへ接続する。旧ルールの表示・再生は旧モデルを維持する。

**入出力:** `solveLabPose(state: Readonly<LabState>): LabPose`の呼び口を維持し、新ファイルから再公開する。`LabPose`に犬と人の独立した姿勢、腰、肩・肘・手先、股・膝・足先、犬の足組・支持パッド・4種の持ち手の座標と到達可否を追加する。計算はThree.jsを参照しない。座標は既存の`(s, x, y)`に統一し、描画の`(s, y, x)`への変換は一か所にする。F02へ渡す`LabPartCollider`は`{partId, shape, localPoints, radius, canBearLoad}`を持ち、形状は球・カプセル・凸箱に限定する。支持パッドの半径0.03m、前後パッドの中心位置±0.35m、前後端±0.50mを共通値とし、胴体・足・靴底・手の形状も同じ定義に明記する。犬種の見た目のメッシュを接触形状に使わない。

**実装方針:** 初めに35・36の到達可能性を3犬種で計算する。現行の短い脚の全長をそのまま維持する制約は置かない。練習専用の共通人モデルの初期案は脚0.75m（腿0.38m・脛0.37m）、腕0.64m（上腕0.33m・前腕0.31m）とする。35・36の足着き時だけ犬がしゃがみ、足置き面を共通の高さ0.55m、腰を約0.68m・犬の横へ0.35m、下ろす足を地面の高さ0m・横0.60mへ移す。靴底を基準に計算し、両脚・後足の背への接触・手の保持・胴体との干渉が同時に成立するかを確認する。これは到達可能性を確かめる初期案であり、現行表示を実測した値や合格済みの姿勢ではない。

肘・膝は逆側へ折れない。全犬種で同じ接触・到達条件を使い、犬の体格差はしゃがむ姿勢とベルトの取り付けで吸収する。途中で手足の長さを伸縮したり、届いたことにする許容値を犬種別に広げたりしない。`getLabRigPoints(rig)`は実際の描画部品のワールド座標を読み出す。到達案が失敗する場合はF01を閉じず、共通モデルの寸法と姿勢を修正して、3犬種の全検査をやり直す。旧ルールの人・犬の寸法は維持し、新ルールには競技でも共通寸法を使う。

- [ ] 先に、技04の犬だけの回転、技34の手と持ち手、技35・36の前足と地面が一致する試験を作る。3犬種×左右の構えで、指定の接触点と表示部品の差が0.01m以下、体・地形へのめり込みが0.01m以内であることを検査する。到達不能な持ち手で成功しない例も入れる。

- [ ] 手足を伸ばして目標へ強制的に合わせたり、図形の中心に置いた目印だけを測って合格させたりしない。表示上の手先・靴底と、判定側の接触点の両方を測る。

## 5. F02 — 移動途中の接触と成立条件を確かめる

**作成:** `src/game/lab-contacts.ts`、`tests/lab-contacts.test.ts`、`tests/lab-boundaries.test.ts`。**変更:** `src/game/trick-lab.ts`、`src/game/trick-lab-terrain.ts`、既存の計算試験2ファイル。

**入出力:** `sampleLabSurface(fixtureId: LabFixtureId, s: number, x = 0): LabSurface | null`に拡張し、既存の2引数の呼出しを維持する。面は`surfaceId`・`regionId`・高さ・勾配・法線・接線を返す。縁・面・側壁は共通の`LabFixtureGeometry`にまとめる。`sweepLabContacts(fixture: LabFixtureGeometry, span: LabMotionSpan): LabContact[]`を作る。`LabMotionSpan`は`{fromUs, toUs, poseAt, motionBounds, colliders}`を持つ。`poseAt(atUs): LabPose`はその区間の移動・符号付き累積回転・手足の到達を計算し、前後の姿勢だけを線形補間しない。`motionBounds(fromUs, toUs)`は各接触形状が区間中に通り得る範囲を返す。結果は部位・障害物ID・面ID・位置・法線・接触時刻・接触開始／終了・荷重支持開始／終了を区別し、現行`LabContact`の情報を落とさず拡張する。

**時刻の決め方:** 競技の5ミリ秒刻みは変更しない。練習も外側の固定刻みを維持し、その中を入力、接触、支持開始・終了、手足の到達、回転・脱出・制動の終了、保持／停止／安定着地の閾値、8秒の終了時刻で分ける。`nextLabBoundaryUs(state, inputs, tickEndUs)`で最も早い境界を求め、発生したイベントで姿勢が変わったら残りの区間を作り直す。外部の描画時刻を新しい積分の区切りにはせず、`advanceLab`は完了できる固定刻みまでを処理し、未完の端数を次へ渡す。接触の根は整数マイクロ秒へ切り上げる。時間は実際の区間の差で積算し、到達したばかりの手へ5ミリ秒分を加える処理を廃止する。

**接触の決め方:** 回転を含む部位の軌跡を調べる。移動範囲が面と重ならない区間を先に除外し、重なる区間は前半から分割して、最初の接触時刻を1マイクロ秒以下の幅まで絞る。非接触の両端を持つ区間でも、範囲が重なる限り途中を調べる。5ミリ秒の区間は最大13段の二分でこの幅に達する。上限到達時の不確定な接触を成功扱いにはせず、該当配置を検査失敗として修正する。側面へ先に当たった場合は失敗とし、犬を横へ移して成功位置に吸着させない。位置を戻す処理は、成立した接触後の食い込み解消に限定する。両支持は同じ障害物で同時に荷重を受けている時間の共通部分を使う。

同じ時刻の順は元計画に合わせ、衝突・転倒→直前区間の支持・滑走・保持の積算→接触の開始・終了→成否の確定→その時刻の入力の`seq`順とする。失敗は取り消さない。ちょうど1.00mで支持が終わる例と0.50秒で中央へ戻す例は、衝突がなければ閾値到達として数える。最初の着地と同時のキャッチ・解除・脱出入力は、着地前に済んだことにしない。この順序を変えるコードには別の仕様変更として理由と反例を必要とする。

- [ ] 滑走0.999／1.000／1.001m、片側支持499／500／501ミリ秒、着地前後1マイクロ秒を確認する。0.50秒だけでなく必要距離1.0mも満たす。安定着地は150ミリ秒と0.2mの両条件を維持する。

## 11. F08 — 固定した確認URLでiPhoneを確かめる

**作成:** `.github/iphone-preview.json`、`scripts/build-iphone-preview.mjs`、`scripts/assemble-pages.mjs`、`tests/review-build.test.ts`、`tests/review-build.spec.ts`、`playwright.review.config.ts`、`docs/iphone-acceptance.md`。**変更:** `.github/workflows/pages.yml`、`.github/workflows/ci.yml`、`src/app-options.ts`、`src/main.ts`、`src/ui/screens.ts`、`src/ranking/production.ts`、`vite.config.ts`、`tests/app-options.test.ts`。この配信基盤だけの実装PRを先に分ける。

**配信方法の提案:** 既存Pagesの`/inubo/review/<sourceCommit>/<artifactId>/`に確認版を置く。候補CIが作った成果物を使い、Pages更新のたびに候補を再ビルドしない。`.github/iphone-preview.json`には`{stage, sourceCommit, runId, runAttempt, artifactId, payloadSha256, expiresAt}`の配列を持つ。`stage`は`interaction`または`release`で、必要な試験を区別する。`sourceCommit`は実際にチェックアウトして検査・ビルドした完全SHAを`git rev-parse HEAD`で取得する。PRの番号やブランチ先端から推測しない。ビルドにはNode・npm・ロックファイルのハッシュも記録する。

基盤のマージ後、候補のゲーム実装とは別PRで成果物の配列だけを更新し、本人のマージ後に公開する。本番のルートはそのmainで作り、確認版は指定の成果物をそのままサブディレクトリへコピーする。同じURLへ別の成果物を置かない。成果物は保存期限を持つため、期限切れ・取得失敗・内容不一致では当該URLに「この確認版は利用できません」と表示し、ゲームを起動しない。本番ルートの更新は継続する。再作成した場合は別のartifactId・URLとし、以前の実機合格を引き継がない。期限を延ばすための課金設定は変更しない。

**保存先の契約:** `BuildContext`を`{mode: 'production' | 'e2e' | 'review', storagePrefix, sourceCommit?, buildId?}`とする。`readPlayOptions(search, context)`は既存の試験用フラグに加えてこの情報を返す。`testBuild`は`mode === 'e2e'`だけで真にする。productionの接頭辞は空文字、e2eは既存の`inubo-test:`、reviewは`inubo:review:<sourceCommit>:<runId>:<runAttempt>:`で固定する。`App`の`browserStorage(opts.testBuild ? ... : '')`を`browserStorage(opts.storagePrefix)`へ変更し、Records・設定・profile・翻訳・RankingClientすべてへ同じ保管先を渡す。同一サイトのサブパスだけでは保存領域は分かれないため、main側の分岐だけで完了にしない。

**確認用ビルド:** `vite build --mode review`で`dist-review/`を作り、専用の`playwright.review.config.ts`からその実物を配信して試す。reviewではtransportを常にnullとし、本番接続先を含めず、`createProductionTransport`もreviewモードを拒否する。環境変数が残っていても本番通信を開始しない。URLパラメーターでこの区分を変更できない。自動操縦・状態書換え用の窓口は公開せず、試験も`window.__inubo`なしで操作する。

## 12. F09 — 犬種差を評価し、資料と完了状態をそろえる

**計測の入出力:** 確認モードだけで、競技の各5ミリ秒の処理後に読み取り専用の`MeasurementSample`（時刻、pathId、u、x、targetX、得点、失敗、適用した入力、当該刻み内の`pathTransitions: {fromPathId, toPathId, atUs, boundaryU}[]`）を計測器へ渡す。経路遷移は実際に道を移った処理点で採取し、刻み後のpathIdだけから推測しない。`advanceRun`には省略可能な第4引数`observeTick?: (sample: Readonly<MeasurementSample>) => void`を追加し、渡す値は計算状態への参照を持たないコピーにする。通常版はこの引数を使わない。観測あり／なしのF00の9走を完全一致させ、計測器の例外は計測失敗として記録し、ゲームの進行に影響させない。

計測区間は直線`pathId=start, u=10→110m`、急カーブ`pathId=mid, u=360→410m`、手すり分岐`pathId=f2-rail, u=420→500m`とする。開始・終了は該当境界以上になった最初の固定刻みの時刻で記録し、分解能は5ミリ秒と明記する。正常な`f2-rail→late`の`u=500`終端通過は遷移履歴で確認し、その刻みで終了を確定してから経路離脱の失敗を調べる。刻み後が`late`でも、正しい終端通過を失敗にしない。別経路・途中離脱は失敗とし、別経路の時間や再進入後の成功で埋めない。入力回数は認識された`steer`・`forward`・`circle`・`line`を`strokeId＋kind`でまとめ、同一操作中の連続通知は重複計上しない。拒否された入力は別欄に残す。

確認版の走行後に、区間ごとの時刻・技点差・失敗・入力回数と候補版情報を表示し、JSONとして端末へ保存できるようにする。操作を代行するボタン、時刻や状態を書き換える窓口は作らない。実機の27区間はこの読み取り結果で測り、映像の目測時間や自動操縦の値と混ぜない。失敗も3回の測定に含め、完了しなかった区間の時間はnullとする。アプリ切替等の測定中断は理由付きで別記し、再測定は元の失敗記録を消さず追加する。

## 13. 試験の範囲と公開判定

| 変更 | 普段の確認 | 候補版の最終確認 |

最終候補では `npm run typecheck`、`npm test`、`npm run build`、`npm run test:e2e` をすべて通す。独立した計算試験と画面試験は別ジョブにできるが、同じ出力ディレクトリを共有しない。通常の変更で無関係な試験を繰り返さず、変更した箇所と共通処理の影響で範囲を決める。既存CIの省略条件を変更する場合は、その変更を専用の差分として検証する。

完了には、各工程の合格資料、独立レビューへの対応、固定コミットの自動検査、iPhone実機の記録をそろえる。実装候補に変更が入った場合は影響する検査をやり直し、新しい確認URLで確かめる。公開後の不具合では候補のコード差分を戻すPRを作り、既存の記録や送信待ちを消して戻す方法は使わない。
